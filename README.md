# 插件管家（dsh-update-guard）

> 更新前先让模型审一遍：**更新了什么、要不要装、会踩什么坑**。
> 决定装，就自动把你这台机器上的本地补丁打回去；补丁对不上，就退回旧版，不让已知 bug 复活。
> 装完要重启，有人替你盯着——起不来会自己再拉，拉不动就明确叫你手动开。
> 新装插件先做安全体检；出过的错记进知识库，同一个坑不踩第二次。

给 DSH（DeepSeek Harness）用的插件。目标只有一条：**这套 DSH + 插件能稳稳地跑**。可以暂时不更新——但绝不更新完就崩。

📖 **[完整使用手册（含 10 个使用场景）→ 使用手册.md](使用手册.md)**
—— 怎么读报告、补丁对不上怎么办、装完后悔怎么退、队列怎么排、踩过的坑记在哪。

## 它解决的到底是什么

插件更新本身不吓人，吓人的是这三件事：

1. **更新把本地修好的 bug 又改回去了。** 你为了绕过一个坑，手工改过插件里的两行，或打过补丁；
   一升级，文件被覆盖，坑回来了。
2. **更新前没人告诉你它会踩什么。** 点「更新」之前，你不知道动的是安装流程、还是锁文件、还是权限。
3. **更新完要重启，你不知道它会不会回来。** 起不来就是一连串手工救援。

这个插件把这三件事都变成了有据可查的流程。

## 十个工具

| 工具 | 干什么 |
|---|---|
| `plugin_update_scan` | 扫一遍装了什么，registry 上哪些有新版本（只读） |
| `plugin_update_review` | 把新旧版本逐文件 diff 喂给模型，产出「装 / 等等 / 跳过」+ 风险清单（只读） |
| `plugin_update_trial` | 在系统临时目录里**真装、真加载**一遍，脏不了你的 profile |
| `plugin_update_apply` | 真装：先快照备份 → 迁移本地补丁 → pnpm install → 装完立刻加载验证 → 任何一步失败**自动回滚**。补丁打不上时会先让模型**重新对准**新版本（三道机械验收，不过就照常回滚） |
| `plugin_update_rollback` | 退回上一次更新前的状态 |
| `plugin_update_scan` / `plugin_patches` | 盘点本地补丁（`patchedDependencies` + `patches/*.patch` 双向核对） |
| `plugin_install_check` | 新装插件的体检，可做**硬拦截**（会遮蔽核心包的直接拦下） |
| `plugin_memory` | 更新档案（谁在什么时候从哪升到哪、成没成、回滚没有）+ 错误知识库 |
| `plugin_queue` | 后台更新队列：等你不用的时候自己动手 |
| `plugin_restart` | 带兜底的安全重启 |

设置页有「插件管家」，四个页签：更新记录 / 错误知识库 / 补丁账本 / 后台队列。
（后台队列页能看队列里排了什么、现在能不能动手、为什么不能，也能删掉某条待办。）

## 几条硬规矩（写进代码，不是写在文档里）

- **补丁修不好就放弃更新**，保留旧版。宁可不上新功能。
- **回滚先斩后奏**：装坏了立刻自动退回去，不等你点确认。
- **试跑必须跑**：慢可以，跳过不行——出问题后再修花的时间和精力更多。
- **重启默认只提示，不自动做**。自动化任务里禁止「自动更新 + 自动重启」。
- **空闲才动手**：没有会话在跑 + 连续安静 2 分钟 + 随时可叫停，三个条件同时满足。
- **重启成功只认新进程**：端口通不算数，必须是新 pid 连续稳定 8 秒。

## 安装

```bash
# profile 目录里
pnpm add -D <本包来源>
```

或把本仓库放进 `local-plugins/`，在 profile 的 `package.json` 里写 `file:./local-plugins/dsh-update-guard`，再 `pnpm install`。

装完重启一次 DSH，设置里就会出现「插件管家」。

## 配置

| 键 | 默认 | 含义 |
|---|---|---|
| `profile` | 当前会话的 profile | 管哪个 profile |
| `queueEnabled` | `true` | 后台队列开关 |
| `queueIntervalMs` | `60000` | 队列多久看一次 |
| `idleQuietMs` | `120000` | 连续安静多久算空闲 |
| `restartAfterApply` | `notify` | 装完后：`notify` 只提示 / `auto` 自动重启 / `never` 什么都不做 |
| `appExe` | 自动识别 | DSH 可执行文件路径（认不出来时手动指定） |
| `installTimeoutSec` | `600` | pnpm install 超时 |
| `patchFix` | `true` | 补丁打不上时让模型重新对准新版本（过不了验收就回滚） |
| `patchFixTokens` | `8000` | 重写补丁时给模型的输出额度 |

## 补丁能被保住，靠的是 pnpm 自己的机制

本地修复统一走 pnpm 的 `patchedDependencies` + `patches/*.patch`：

- 每次 install 自动重放，不是靠人记得；
- 补丁 key 的版本和实装版本不符时，pnpm 会直接 `ERR_PNPM_UNUSED_PATCH` **报错中止**——不给你「悄悄少打一个补丁」的机会；
- 插件的账本会正反核对：登记的有没有文件、有文件的有没有登记。

> 建议每个补丁旁边放一份 `intent.md`，写清「为什么打这一刀」。半年后你会感谢自己。

### 补丁打不上怎么办

升级后上游挪了代码、改了参数，补丁的上下文就对不上了。这时候插件会做一次「重新对准」：

1. 从 registry 拉新版本的**原始文件**（不信任 node_modules 里可能半新半旧的）；
2. 把旧补丁 + intent + 新版原文喂给强档模型，要求它**只挪位置、不许改行为、不许删功能**；
3. 三道机械验收，任何一道不过就**当没发生过**：
   - 新补丁必须能干净地打在新版原文上；
   - 原补丁新增的函数 / 常量名，一个都不能少；
   - 只允许改一个文件（多文件补丁留给人）。
4. 验收通过才写盘，**先备份旧补丁**（`.patch.bak-时间戳`），然后再装一遍。

过不了就照旧例：放弃这次更新，保留旧版。设置里 `patchFix` 可以整个关掉。

`intent.md` 的格式（`<profile>/patches/<包名>@<版本>.intent.md`）：

```markdown
---
summary: 一句话说清这补丁修什么
issue: "上游 issue 号（有就写）"
severity: 高 / 中 / 低
retireWhen: 什么条件下可以删掉这个补丁
---
正文：症状、根因、改了什么、怎么验证上游已经自己修了。
```

## 兼容性

- DSH 插件 API：`@deepseek-ai/cordis` ^4.0.1
- Node：>= 22
- 平台：Windows 为主（重启帮手用了 `tasklist` / `netstat` / `taskkill`），Linux/macOS 有降级分支但未在真机验证
